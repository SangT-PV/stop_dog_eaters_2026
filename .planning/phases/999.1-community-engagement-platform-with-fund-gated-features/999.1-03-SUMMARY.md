# Phase 999.1 Plan 03: Comment Submission & Interaction Summary

**One-liner:** Implemented interactive comment submission with rich formatting toolbar, threaded replies, like button persistence, and optimistic pending comment UI

## What Was Built

### Task 1: Comment Submission Form with Formatting Toolbar

**Extended `website/js/comments.js` (+400 lines):**

#### 1. Comment Form Rendering (`renderCommentForm()`)
- Two variants: main form (top of section) and inline reply form (nested)
- **Form structure:**
  - Name input (1-100 chars, required)
  - Email input (validated email format, not displayed publicly)
  - Formatting toolbar (Bold, Italic, Underline, Emoji buttons)
  - Textarea with live character counter (0/2000)
  - Submit button ("Post Comment" or "Post Reply")
  - Cancel button (reply forms only)
  - Privacy notice: "Comments are reviewed before appearing publicly. Your email is never displayed."

#### 2. Formatting Toolbar (`handleFormatting()`, `showEmojiPicker()`)

**Text formatting:**
- **Bold** (`**text**`) - Wraps selected text in double asterisks
- *Italic* (`*text*`) - Wraps selected text in single asterisks
- <u>Underline</u> (`__text__`) - Wraps selected text in double underscores
- Formatting markers stored as plain text, rendered as HTML via `renderCommentContent()`

**Emoji picker:**
- 12 common emojis: ❤️ 👍 🔥 👏 🙏 😢 😠 🤔 ✓ ⭐ ✨ 👋
- Positioned below toolbar in absolute dropdown (6-column grid)
- Click emoji → inserts at cursor position
- Click outside → closes picker

#### 3. Comment Content Rendering (`renderCommentContent()`)

**Markdown parsing order:**
1. `escapeHTML()` first (XSS protection)
2. Convert newlines to `<br>`
3. Apply formatting patterns:
   - `**text**` → `<strong>text</strong>`
   - `*text*` → `<em>text</em>` (not inside `**`)
   - `__text__` → `<u>text</u>`

**Why this order:** Escape first prevents XSS, then apply formatting to safe plain text.

#### 4. Comment Submission (`submitComment()`)

**Validation:**
- Name: 1-100 characters, required
- Email: Regex `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` (standard email pattern from main.js)
- Content: 1-2000 characters, required

**UUID generation:**
- Modern browsers: `crypto.randomUUID()`
- Fallback: `generateUUID()` using Math.random() for older browsers

**Comment object structure (per _schema.json):**
```json
{
  "id": "uuid-v4",
  "post_slug": "post-id",
  "parent_id": "uuid-or-null",
  "author_name": "string",
  "author_email": "string",
  "content": "plain text with markdown markers",
  "likes": 0,
  "status": "pending",
  "created_at": "ISO 8601",
  "moderated_at": null,
  "moderated_by": null
}
```

**Storage strategy (static site with no backend):**
- Save to `localStorage` key `sde-pending-comments` (array)
- Moderation dashboard (Plan 04) reads from this queue
- Optimistically render pending comment with "Pending Review" badge
- Alert: "Thank you! Your comment is being reviewed and will appear once approved."
- Clear form after submission
- Remove inline reply form if applicable

#### 5. Like Button Persistence (`handleLike()`, `getLikedComments()`, `saveLikedComments()`)

**localStorage structure:**
- Key: `sde-liked-comments`
- Value: JSON array of comment IDs `["uuid1", "uuid2", ...]`
- Converted to Set for O(1) lookups

**Toggle behavior:**
- If not liked: Add to set, increment count, add `.liked` class, fill heart icon
- If already liked: Remove from set, decrement count, remove class, unfill heart
- Persist to localStorage after every toggle

**Why client-side only:** Static site has no server persistence. Likes are local to each user's browser for MVP.

#### 6. Threaded Replies (`handleReplyClick()`)

**Inline reply form logic:**
- Remove any existing reply form (only one active at a time)
- Find parent comment's `.comment-thread` div
- Insert `renderCommentForm(parentId)` inside `.comment-replies` div
- If no replies div exists, create one
- Focus name input
- Attach event listeners via `attachFormListeners()`

**Max depth enforcement:**
- Reply button only rendered if `depth < this.maxDepth` (3 levels)
- Prevents excessive nesting on mobile

#### 7. Event Delegation (`attachEventListeners()`)

**Single container listener on `#comments-container`:**
- `.comment-like-btn` click → `handleLike(commentId)`
- `.comment-reply-btn` click → `handleReplyClick(commentId)`
- `.comment-cancel-reply` click → remove `.reply-form`
- `.toolbar-btn` click → `handleFormatting(textarea, format)`
- `.comment-form` submit → `submitComment(form)`
- `.comment-textarea` input → `updateCharCount(textarea)`

**Why event delegation:** Forms are dynamically added (reply forms), so one-time listeners would miss them. Delegation on container catches all events.

#### 8. Optimistic UI (`getPendingComments()`, `renderComments()`)

**Pending comment display:**
- Fetch pending comments from `localStorage` filtered by `post_slug`
- Merge with approved comments from server/localStorage (Plan 04 integration)
- Render pending comments with "Pending Review" badge (yellow pill)
- User sees their submission immediately, even before moderation approval

**Updated `renderComments()` logic:**
```javascript
const approvedComments = this.comments.comments.filter(c => c.status === 'approved');
const pendingComments = this.getPendingComments();
const allDisplayComments = [...approvedComments, ...pendingComments];
```

**Updated `renderCommentNode()` logic:**
- Check `comment.status === 'pending'` → add `.comment-pending-badge`
- Check `getLikedComments().has(comment.id)` → add `.liked` class, fill heart icon
- Hide Reply button if at max depth

## Technical Decisions

### 1. Markdown Storage Format
**Decision:** Store formatting as plain text markers (`**`, `*`, `__`) instead of HTML.

**Why:**
- Simpler for moderators to review in dashboard (Plan 04)
- Prevents XSS injection via rich text
- Easier to edit/modify before approval
- Clean JSON storage (no HTML tags)

**Rendering:** `renderCommentContent()` parses markers on display only.

### 2. Emoji Picker Design
**Decision:** 12 curated emojis (not full Unicode picker).

**Why:**
- Covers 90% of use cases (heart, thumbs up, thinking, etc.)
- Fast to render (no lazy loading or search)
- Mobile-friendly (6-column grid, large tap targets)
- No external library dependency

### 3. localStorage Persistence Strategy
**Decision:** Two separate keys for pending and liked comments.

**Why:**
- `sde-pending-comments` is a queue (moderation reads and removes)
- `sde-liked-comments` is persistent state (never cleared automatically)
- Separation prevents accidental clearing of user likes when approving comments

### 4. Event Delegation Pattern
**Decision:** Single `addEventListener` on container for all form events.

**Why:**
- Reply forms are dynamically inserted/removed
- Attaching listeners to each element individually would miss new forms
- Performance: One listener vs. hundreds
- Code clarity: All event handling in one place (`attachEventListeners()`)

### 5. Optimistic UI for Pending Comments
**Decision:** Show pending comments with badge immediately after submission.

**Why:**
- User feedback: "Your comment is visible (to you)"
- Reduces perceived latency
- Encourages engagement (user sees their contribution)
- Badge clearly indicates "not live yet" status

### 6. UUID Generation Fallback
**Decision:** Use `crypto.randomUUID()` with fallback to Math.random-based generator.

**Why:**
- Modern browsers support `crypto.randomUUID()` (Chrome 92+, Firefox 95+)
- Fallback ensures compatibility with older browsers
- UUID v4 format prevents collisions (even client-side)

### 7. Email Validation Regex
**Decision:** Reuse pattern from `main.js` petition form.

**Why:**
- Consistency across site
- Already tested and working
- Simple pattern (not RFC 5322 compliant, but sufficient for basic validation)

## Known Limitations

1. **No server persistence** — Comments stored in localStorage only. Need backend API to truly save.
2. **No real-time updates** — Must refresh page to see newly approved comments.
3. **No edit/delete** — Once submitted, can't modify or remove own comment.
4. **No like count sync** — Likes are per-browser. No aggregation across users.
5. **No spam protection** — Could submit unlimited comments. Rate limiting needed in future.
6. **No image upload** — Text-only comments for MVP.
