**`rejectComment(commentId)`:**
- Removes from `sde-pending-comments` localStorage
- Animates UI with red flash (`.rejecting` class), fades out, removes element

**Similar logic for `approvePost()` and `rejectPost()`** — stores in `sde-approved-community-posts` instead.

### Task 2: Update comments.js to Merge localStorage and JSON Comments

**Modified `website/js/comments.js`:**

**Updated `fetchComments()` method:**
```javascript
async fetchComments() {
  // 1. Fetch server-side comments from JSON file
  let serverComments = [];
  try {
    const response = await fetch(this.commentsUrl);
    if (response.ok) {
      const data = await response.json();
      serverComments = data.comments || [];
    }
    // 404 = treat as empty (new posts won't have files yet)
  } catch (error) {
    console.warn('Failed to fetch server comments:', error);
  }

  // 2. Fetch locally-approved comments from moderation dashboard
  const localKey = `sde-comments-${this.postSlug}`;
  const localCommentsStr = localStorage.getItem(localKey);
  const localApprovedComments = localCommentsStr ? JSON.parse(localCommentsStr) : [];

  // 3. Merge and deduplicate
  const merged = this.mergeLocalAndServerComments(serverComments, localApprovedComments);
  this.comments = { post_slug: this.postSlug, comments: merged };
}
```

**Added `mergeLocalAndServerComments()` helper:**
- Creates a `Map` of approved comments keyed by `comment.id`
- Adds server comments first (highest priority)
- Adds local approved comments only if not already in server (deduplication)
- Returns merged array

**Benefits:**
- Comments approved via moderation dashboard appear immediately (from localStorage)
- Comments committed to JSON files (via export) also appear
- Server version takes precedence if same comment exists in both (prevents divergence)
- Graceful 404 handling (new posts without comment files work correctly)

## Technical Decisions

### 1. Dual localStorage Keys for Approved Comments

**Decision:** Store approved comments in TWO keys: global (`sde-approved-comments`) and per-post (`sde-comments-{slug}`).

**Why:**
- Global key: Used by export feature to generate downloadable JSON files
- Per-post key: Used by `comments.js` to display comments immediately after approval (without waiting for JSON file commit)
- Avoids having to scan entire global array for each post

**Trade-off:** Slight redundancy, but improves performance and keeps concerns separated.

### 2. SessionStorage for Auth Token (Not LocalStorage)

**Decision:** Store `sde-mod-auth` token in `sessionStorage`, not `localStorage`.

**Why:**
- SessionStorage resets on browser close (better security)
- Moderator has to re-enter password after closing tab (acceptable UX for admin tool)
- Prevents long-lived auth tokens in localStorage (which could be exploited by XSS)

### 3. Simple Password Check (No Backend)

**Decision:** JavaScript password check with SHA-256 hashing, no backend validation.

**Why:**
- This is a static site with no backend
- Data (JSON files) is publicly accessible anyway
- Goal is to deter casual access, not provide real security
- Moderators (Tuan Anh) understand this is not a secure system

**Future:** If community grows, migrate to real backend with OAuth/JWT.

### 4. Export to JSON (Not Auto-Commit)

**Decision:** Manual export feature that generates downloadable JSON files, rather than auto-writing to disk.

**Why:**
- Static site cannot write files to server (no backend)
- Moderator must manually download and commit files to repo
- Gives moderator final review before approved comments go live in production

**Benefit:** Moderator has full control over what gets committed.

### 5. Deduplication by ID (Server Wins)

**Decision:** When merging server + localStorage comments, prefer server version if same ID exists in both.

**Why:**
- Server is source of truth (committed to repo)
- Prevents divergence if comment metadata was edited after export
- localStorage acts as temporary cache until export/commit happens

## Known Limitations

1. **Not real security** — JavaScript password check can be bypassed by inspecting code or localStorage. This is acceptable for a small campaign with trusted moderators.
2. **No backend API** — All storage is localStorage + JSON files. Scaling to 1000s of comments requires backend migration.
3. **No real-time sync** — Approved comments only appear on other tabs after page refresh (no WebSocket/SSE).
4. **Manual export required** — Moderator must download and commit JSON files manually. No auto-commit.
5. **No edit/delete after approval** — Once approved, comments are immutable (until manually edited in JSON file).
