# Phase 999.1 Plan 01: Community Data Contracts & Comment UI Summary

**One-liner:** Established JSON schemas for all community features and implemented read-only threaded comment system with $1K fund-gating

## What Was Built

### Data Contracts (Task 1)
Created comprehensive JSON schemas for the entire community engagement platform:

**1. Comments System (`website/data/comments/`)**
- `_schema.json` — Comment data structure with threading support
- Schema includes: `id` (uuid), `post_slug`, `parent_id` (for replies), `author_name`, `author_email`, `content`, `likes`, `status` (pending/approved/rejected), timestamps, moderation fields
- `example-post-comments.json` — Empty example file

**2. Community Posts (`website/data/community-posts/`)**
- `_schema.json` — User-submitted article schema (reuses blog post format)
- Approved posts become standard blog posts with `author='Community'` and `tag='Community'`
- `submissions.json` — Empty submission queue

**3. Feature Voting (`website/data/votes/`)**
- `_schema.json` — Voting system structure ($10K+ tier)
- `features.json` — 4 initial feature proposals:
  - Vietnamese translation
  - Local chapter toolkit
  - Investigative journalism fund
  - School education program

**4. Community Configuration (`website/data/community-config.json`)**
- Controls fund-gated feature unlocking
- 4 tiers defined:
  - **$1K**: Blog Discussion Sections (comments)
  - **$2.5K**: Community Post Creation
  - **$5K**: AI Engagement Bot
  - **$10K+**: Feature Voting System
- `current_unlocks` object tracks which features are enabled
- `celebration_banner` placeholder for milestone announcements

### Comment Rendering Module (Task 2)
Implemented `website/js/comments.js` (353 lines):

**Features:**
- **Class-based module pattern** (follows `fund-tracker.js` convention)
- **Fund-gating check**: Fetches `community-config.json` to check unlock status
- **Locked state UI**:
  - Lock icon, explanation text, "Support the Campaign" CTA
  - Progress bar showing current funds vs $1K threshold
  - Reads `data/funds.json` to calculate progress percentage
- **Threaded comment rendering**:
  - Builds comment tree from flat array using `parent_id`
  - Max nesting depth: 3 levels (prevents excessive indentation)
  - Only renders `status: 'approved'` comments
- **UI elements per comment**:
  - Avatar circle (first letter, brand color hash)
  - Author name (bold), relative timestamp ("2 hours ago")
  - Content (plain text with newlines → `<br>`)
  - Like button (heart icon + count, local increment)
  - Reply button (placeholder for Plan 03)
- **Empty state**: "No comments yet. Be the first to share your thoughts!"
- **Utility methods**:
  - `escapeHTML()` — XSS protection
  - `timeAgo()` — Relative timestamps (just now, X minutes/hours/days/weeks ago, or formatted date)
  - `getAvatarColor()` — Hash name to 6 brand colors

**CSS Styles (`website/css/style.css` +202 lines):**

## Technical Decisions

### 1. Comment Tree Building
Built two-pass tree construction:
1. First pass: Create map of `comment.id → comment node`
2. Second pass: Attach children to parent nodes via `parent_id`
3. Result: Nested array structure for recursive rendering

**Why:** Efficient O(n) algorithm, easier to enforce depth limits.

### 2. Avatar Color Hash
Used simple character code summation hash modulo 6 brand colors.

**Why:** Consistent colors per author, no external library needed, visually diverse.

### 3. Local-Only Like Increment
Like button increments count in DOM only (no persistence).

**Why:** Backend submission logic comes in Plan 03. This plan is read-only rendering.

### 4. 404 Handling for Missing Comment Files
If `data/comments/{slug}-comments.json` returns 404, treat as empty array.

**Why:** New posts won't have comment files yet. Graceful degradation.

### 5. Max Depth = 3 Levels
Hardcoded depth limit in `renderCommentNode()`.

**Why:** Prevents excessive indentation on mobile. Most discussions don't exceed 3 levels.
